# 公开内容边界

## 目的

本文定义 QA Workbench 源码仓库允许公开的内容、禁止内容和发布检查。基本原则是：公共仓库只包含通用实现、合成示例和公开开发文档；无法确认可公开性的内容不进入仓库。

## 允许公开的内容

- 通用的 TestCase、OpenAPI 和 Arazzo 目录发现与解析逻辑；
- 测试选择、execution plan、结构化事件和状态管理；
- 本机 Workbench 的通用 UI 与服务端实现；
- provider、runner adapter 和 report 的公共契约；
- 与具体业务无关的单元测试和开发配置；
- 从零编写的 synthetic fixture、示例规范和演示页面。

## 禁止公开的内容

### 数据和测试资产

- SQL dump、数据库快照、SQLite 或其他本地数据库；
- 真实或可还原的用户、请求、响应、日志等业务数据；
- 真实项目的 OpenAPI、Arazzo、TestCase、验收规则和缺陷复现资料；
- 截图基线、视觉 diff、trace、HAR、录屏、DOM 快照和浏览器 storage state；
- 无法证明可公开来源的所谓“脱敏”数据或素材。

### 身份和基础设施

- token、Cookie、密码、签名密钥、私钥和测试账号；
- 真实邮件地址、角色映射、环境身份和个人工作区路径；
- 非公开域名、IP、代理、数据库 DSN、集群、日志库和 CI runner 标识；
- 项目专用请求头、内部路由、部署脚本和安全例外。

### 历史和第三方内容

- 非公开问题记录、代码审查、决策记录和人员信息；
- 未确认许可证或上游项目的第三方源码、字体、图标、图片或生成资产；历史快照缺失 revision 时必须显式标记 unknown，不得伪造来源；
- `node_modules`、第三方二进制、构建产物和离线依赖包；
- 从真实资产批量改名、但仍能还原业务逻辑的 fixture。

## 通用化规则

| 项目侧概念 | 公共仓库中的表达 |
| --- | --- |
| 固定模块和规范目录 | `ProjectManifest` 配置 |
| 环境和身份 | `EnvironmentProvider` 与 secret reference |
| 专用请求头和鉴权 | 项目侧 runner adapter |
| 固定测试命令 | `RunnerAdapter` 能力声明 |
| 项目报告字段 | 通用结构化事件 |
| 真实规范与 TestCase | 从零编写的 synthetic fixture |

公共核心只表达可由两个以上独立使用场景复用的语义。项目侧扩展可放在独立仓库或本机忽略目录中，不能让公共核心依赖其存在。

## 合成示例要求

- 使用虚构项目、模块、域名和身份；
- 默认仅访问 loopback、保留示例域名或完全使用 mock；
- 数据量最小，同时覆盖成功和失败路径；
- 不沿用真实业务 ID、字段组合、响应内容或截图；
- 在没有私密环境变量和相邻仓库时可以完整验证。

## 源码分发边界

本项目只发布源码，并通过 `package.json` 与 `pnpm-lock.yaml` 声明依赖。第三方组件由使用者自行安装，并继续适用各自版本的许可证。仓库不得提交 `node_modules`、bundle、容器镜像或离线依赖；确需复制或生成到仓库内的第三方源码，必须在 `THIRD_PARTY_NOTICES.md` 记录许可证、范围和上游来源。新增或同步时必须记录 revision；无法追溯的历史快照只能如实标记 unknown，并在再次同步前补齐来源。

若发布形态发生变化，应以最终产物为对象重新执行许可证扫描，并为实际分发的第三方代码附带所需许可证、版权和 NOTICE。

## 每次发布检查

1. 检查新增文件类型、大小和 Git 跟踪状态。
2. 扫描专有标识、非公开域名、私有 IP、个人路径和环境身份。
3. 对当前树和完整 Git 历史运行 secret scanner。
4. 确认路径不逃逸仓库，默认流程不依赖相邻目录。
5. 执行冻结安装、测试、构建、生产依赖漏洞和许可证审计。
6. 从候选 commit 建立独立 clone，重复验证。

任何检查存在未处理项时，不应发布新的源码版本。
