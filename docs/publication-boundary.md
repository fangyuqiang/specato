# Publication Boundary

## Purpose

This policy defines what may enter the public Specato repository, what is prohibited, and which checks block publication. The public repository contains reusable implementation, synthetic examples, and public development documentation only. Content whose publication status cannot be proven must stay out.

AI-generated content is not automatically safe or original. TestCases, automation code, fixtures, documentation, and adapters generated by an AI coding assistant must satisfy the same provenance, confidentiality, license, and review requirements as human-authored content.

## Allowed content

- Reusable discovery and parsing for TestCase, OpenAPI, Arazzo, and related specifications.
- AI-readable contracts for generation, validation, execution planning, evidence, and reporting.
- Test selection, structured events, state management, and safe adapter interfaces.
- General-purpose local Workbench UI and server implementation.
- Public provider, runner-adapter, and report contracts.
- Unit tests and development configuration independent of a real product.
- Synthetic fixtures, example specifications, and demo pages authored from scratch.
- Documentation that clearly separates delivered behavior from design and roadmap intent.

## Prohibited content

### Data and test assets

- SQL dumps, database snapshots, SQLite files, or other local databases.
- Real or reversible users, requests, responses, logs, or business data.
- Real-project OpenAPI, Arazzo, TestCases, acceptance rules, or defect reproductions.
- Screenshot baselines, visual diffs, traces, HAR files, recordings, DOM snapshots, or browser storage state.
- “Anonymized” data or assets whose public provenance and irreversibility cannot be demonstrated.

### Identity and infrastructure

- Tokens, cookies, passwords, signing keys, private keys, or test accounts.
- Real email addresses, role mappings, environment identities, or personal workstation paths.
- Private domains, IPs, proxies, database DSNs, clusters, log stores, or CI runner identities.
- Product-specific headers, internal routes, deployment scripts, or security exceptions.

### History and third-party content

- Private issues, code review records, decisions, or personnel information.
- Third-party source, fonts, icons, images, or generated assets without a verified license and upstream source.
- `node_modules`, third-party binaries, bundles, containers, build output, or offline dependencies.
- Fixtures produced by renaming real assets while retaining recognizable business logic.
- AI-generated material that reproduces private context, copyrighted source, or unverifiable provenance.

## Generalization rules

| Project-side concept | Public repository representation |
| --- | --- |
| Fixed module and specification paths | `ProjectManifest` configuration |
| Environment and identity | `EnvironmentProvider` plus secret references |
| Product-specific authentication | Project-side runner adapter |
| Fixed test command | `RunnerAdapter` capability declaration |
| Product report field | General structured execution event |
| Real specification or TestCase | Synthetic artifact authored from explicit public intent |
| AI-tool-specific prompt or state | Repository-neutral instruction, schema, or adapter |

The public core should contain semantics reusable by at least two independent scenarios. Private adapters may live in project repositories or ignored local paths, but the public core must not depend on them.

## Synthetic example requirements

- Use fictional projects, modules, domains, identities, and data.
- Access loopback, reserved example domains, or mocks only.
- Keep the dataset minimal while covering success and failure paths.
- Do not preserve real IDs, field combinations, response content, screenshots, or recognizable workflow structure.
- Verify without private environment variables, neighboring repositories, or organization services.
- Review AI-generated examples against the original specification and this publication boundary before commit.

## Source distribution boundary

The project currently distributes source and declares npm dependencies through `package.json` and `pnpm-lock.yaml`. Users install those dependencies themselves, and each locked component remains subject to its own license.

Do not commit `node_modules`, bundles, containers, or offline dependency archives. Third-party source copied or generated into the repository must retain its required license and copyright text and be recorded in `THIRD_PARTY_NOTICES.md` with scope, upstream source, and exact revision. If a historical snapshot lacks a revision, mark it `unknown`; never invent provenance.

If the distribution model changes, run license analysis against the actual shipped artifact and include all required licenses, copyrights, notices, and an SBOM where appropriate.

## Publication checklist

1. Review added file types, sizes, generated output, and Git tracking state.
2. Scan for private identifiers, internal domains, private IPs, personal paths, and environment identities.
3. Run a secret scanner on the candidate tree and publishable Git history.
4. Confirm that paths remain repository-contained and default workflows require no adjacent repository.
5. Audit locked dependency vulnerabilities and licenses, plus vendored-source notices.
6. Perform frozen installation, tests, and production build from an isolated checkout.
7. Review AI-generated artifacts for specification fidelity, provenance, and accidental private-context reproduction.
8. Confirm that each maintained document has synchronized English and Simplified Chinese versions.

Do not publish when any check has an unresolved finding.
